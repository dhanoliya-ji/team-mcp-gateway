1. The task in simple words

Urumi asked us to build a small platform with four layers:

  1. A store. One online shop (WordPress + WooCommerce) running on Kubernetes.
  2. Our own WooCommerce MCP server. A program we write ourselves that gives AI tools to read and change the shop's products and orders.
  3. A gateway and a dashboard. The admin adds MCP servers once. The gateway connects to all of them and shows all their tools through one address. Each team member uses their own API key.
  4. A chat agent. A chat box in the dashboard. An AI model answers questions by calling the same tools through the gateway.

Rules: everything runs in Kubernetes, installed with Helm. The same chart must work on a laptop (Kind) and on a server (k3s). No passwords in the code. Every tool call goes into an audit log.

The short version: one door (the gateway) in front of many MCP servers. Each person has their own key to the door. The door keeps the real keys of the servers hidden, writes down every visit, and can lock out a person or a server at any time.

5. The order we built things in

We followed the advice "a working core is worth more than an unfinished bonus". We built from the bottom up and tested each layer before the next. Every small step is its own Git commit.

  1. Repo start: README, .gitignore, .gitattributes (Linux line endings, so shell scripts work in containers).
  2. WooCommerce MCP server: REST helper -> tools -> HTTP server -> Dockerfile. Tested tools/list and ping locally with curl.
  3. Notes and utils MCP servers: same pattern.
  4. Kind cluster with ingress-nginx (in the background while coding).
  5. Gateway: config -> database -> security helpers -> upstream client -> auth -> audit -> MCP endpoint -> SSRF check -> routes (login, servers, users, keys, audit) -> chat agent -> seed -> main file. Tested locally with two upstreams and one dead one.
  6. Dashboard: project -> API helper -> app shell with login -> styles -> pages (servers, keys, members, audit, chat) -> Dockerfile.
  7. Helm chart: Chart.yaml, values, helpers, Secret, MariaDB, WordPress, setup Job, 3 MCP servers, gateway, dashboard, Ingress, NetworkPolicies, NOTES, values files.
  8. First install, fix problems (section 14), full test with a script.
  9. Stand-out: tool permissions; hardening; docs; GitHub Actions; upgrade/rollback test.

6. Part 1: our WooCommerce MCP server

Folder: woo-mcp-server/. We wrote it ourselves (no existing WooCommerce MCP plugin).

6.1 How it talks to the store, and why

It uses the WooCommerce REST API (/wc/v3/products, /wc/v3/orders) over plain HTTP inside the cluster, with a consumer key and secret (Basic auth).

  • Why REST and not WP-CLI? REST is the official API for products and orders, works over the network, and lets the MCP server be its own small pod with its own limits and firewall rules. WP-CLI would need to run inside the WordPress pod.
  • Why ?rest_route=? It works even if WordPress "pretty links" are not set up.
  • Why the X-Forwarded-Proto: https header? WooCommerce accepts key + secret only on HTTPS. Inside the cluster we use plain HTTP. The WordPress image trusts this header and acts as if the request was HTTPS. This is safe because WordPress is only reachable from the ingress controller and the woo-mcp-server pod (NetworkPolicy).

6.2 Files

"Today": the server knows the store time zone (STORE_TIMEZONE, default Asia/Kolkata, also set in WordPress). It computes today's date in that zone and asks for orders between 00:00:00 and 23:59:59. So "what orders came in today" matches what the shop owner sees.

6.4 Stateless Streamable HTTP (the core code)

app.post("/mcp", checkToken, async (req, res) => {
  const server = new McpServer({ name: "woocommerce", version: "1.0.0" });
  addTools(server);
  const transport = new StreamableHTTPServerTransport({
    sessionIdGenerator: undefined,  // stateless: no sessions
    enableJsonResponse: true,       // plain JSON answers
  });
  res.on("close", () => { transport.close(); server.close(); });
  await server.connect(transport);
  await transport.handleRequest(req, res, req.body);
});

Why stateless? Each request stands alone, so there is nothing to keep in memory, any pod can answer, and the code is short. GET and DELETE on /mcp answer 405 (they are only for sessions/streams).

8.1 Tool aggregation

Every 15 seconds the gateway connects to every enabled server at the same time (Promise.allSettled), lists its tools, and saves the result. tools/list on the gateway reads this saved list, so it is fast and never waits for a slow server.

8.2 Name collisions

Our scheme: every tool becomes <server-name>__<tool-name>. Server names may only use a-z, 0-9 and "-" (no "_"), so splitting at the first "__" is always right. Example: woocommerce__ping, notes__ping, utils__ping are three different tools.

8.3 Timeouts and dead servers

  • Connect + list: 5 seconds. Tool call: 20 seconds. After that the caller gets: Call to 'utils' failed: Timeout: the server did not answer in time.
  • A dead server becomes Unreachable with the reason (for example "Connection refused" or "Timeout"). Its tools leave the list. Other servers are not affected, because every check and every call is separate.
  • Disabled server: tools leave the list, and direct calls get "Server 'x' is disabled".

8.4 Tool permissions (stand-out item 2)

An admin clicks a tool in the dashboard to lock it ("admin only"). Locked tool names are stored per server. For members, locked tools are hidden from tools/list and rejected if called directly ("You are not allowed to use ..."), and the rejection is in the audit log.

9. Part 4: the chat agent and its tool loop

File: gateway/src/chat.js.

Browser --POST /api/chat (login token, messages)--> gateway
  1. MCP client --> http://127.0.0.1:4000/mcp  with  Authorization: Bearer <the user's login token>
     (so the agent IS the logged-in user: same tools, same permissions, same audit log)
  2. tools = client.listTools()  --> turn into LLM "function" tools
  3. LOOP (max 8 rounds):
        answer = LLM(messages, tools)
        if answer has no tool calls  -> return answer + list of tool calls
        for each tool call:
            result = client.callTool(name, args)   (goes through the gateway: checks + audit)
            add result to messages as role "tool"
  4. The UI shows the answer and, under it, every tool that was called (name, inputs, result).
  • Why call our own /mcp instead of calling functions directly? Then the agent follows exactly the same path as Claude Code: same auth, same permissions, same audit. Nothing talks to the upstream servers except the gateway.
  • LLM: any OpenAI-style "chat completions" API. Default Groq (free). The key is in a Secret (llm-secret) and only the gateway pod has it.
  • Safety: the system prompt says tool results are data, not orders. Each tool result sent to the model is cut to 8 KB. Max 8 rounds.

11.1 Probes, requests and limits

Every workload has a readiness and a liveness probe, and CPU/memory requests and limits (set in values.yaml). Example: WordPress requests 100m CPU / 256Mi and may use up to 1 CPU / 768Mi. The small MCP servers request 20m / 48Mi.

11.2 Storage

Three volumes: MariaDB data, WordPress files (plugins, uploads), gateway SQLite file. They survive pod restarts and Helm upgrades. The storage class is a value: Kind's default locally, local-path on k3s.

11.3 Local domains

We use localtest.me: public DNS where every name under it points to 127.0.0.1. Kind maps ports 80/443 of the laptop to the ingress controller. So http://store.localtest.me and http://dashboard.localtest.me work with no hosts file changes.

12. How one tool call travels, step by step

Example: user B in Claude Code asks "what orders came in today?"

  1. Claude Code sends POST http://dashboard.localtest.me/mcp with Authorization: Bearer mcpgw_... and the JSON-RPC message tools/call, name woocommerce__list_orders, arguments {"date":"today"}.
  2. The Ingress sends /mcp to the gateway Service (allowed by NetworkPolicy: from the ingress namespace).
  3. requireMcpAuth hashes the key, finds it, checks it is not revoked and the user is active. The request now knows "this is user B".
  4. The gateway's MCP server splits the name: server woocommerce, tool list_orders. Checks: server exists, enabled, tool exists, B's role may use it.
  5. callUpstreamTool decrypts the WooCommerce MCP token, opens an MCP client to http://woo-mcp-server:3000/mcp (allowed: only from the gateway), runs initialize and tools/call with a 20 s timeout.
  6. The WooCommerce MCP server checks the token, computes today's date in the store time zone, and calls GET http://wordpress/?rest_route=/wc/v3/orders&after=...&before=... with the consumer key/secret (allowed: woo-mcp -> wordpress).
  7. WordPress reads MariaDB (allowed: wordpress -> mariadb) and returns the orders.
  8. The answer goes back the same way. The gateway writes the audit row (user B, mcp-client, woocommerce, list_orders, time, duration, ok) and returns the result to Claude Code.

13. Security: keys, secrets, isolation

13.1 Where secrets live

SecretStored as
DB passwords, WP admin password, WooCommerce key/secret, MCP tokens, encryption key, first admin passwordKubernetes Secret app-secrets (random, made at install)
LLM API keyKubernetes Secret llm-secret (you create it)
Upstream credentials inside the gatewayAES-256-GCM encrypted in SQLite
User API keys and login tokensSHA-256 hash only (key shown once)
Dashboard passwordsscrypt hash with salt

No password is in Git or in a values file. The browser and MCP clients never get an upstream credential.

13.2 What a member can and cannot do

  • Can: log in, generate and revoke their own API keys, use all allowed tools (dashboard chat or external client), see their own audit rows, see the server list (without secrets).
  • Cannot: add/edit/remove servers, invite or disable users, see other people's keys or audit rows, use locked (admin-only) tools, see any upstream credential, reach any MCP server directly.

13.3 Public vs internal (and how it is enforced)

  • Public: only the two Ingress hosts (store, dashboard with /api and /mcp).
  • Internal only: MariaDB, the three MCP servers (ClusterIP, no Ingress).
  • NetworkPolicies (enforced by the cluster network): deny all incoming; allow ingress controller -> WordPress/dashboard/gateway; WordPress + setup Job -> MariaDB; woo-mcp -> WordPress; gateway only -> MCP servers. Egress: woo-mcp may only reach WordPress + DNS; notes/utils only DNS.
  • Tested: a random pod in the namespace could not connect to woo-mcp-server:3000; the gateway could.
  • Containers: all non-root. Our images also: read-only root filesystem, all Linux capabilities dropped, no privilege escalation.

13.4 If an admin adds a malicious MCP server

  • Its tools are namespaced (evil__...), so it cannot replace woocommerce__* tools.
  • It only gets its own credential, never user keys (we do not pass client tokens through).
  • Descriptions are labeled with the server name and cut to 1000 characters. The chat agent is told tool results are data. (Prompt injection is still a real risk; models can be fooled.)
  • Timeouts stop it from hanging the gateway. The SSRF check stops URLs that point to localhost or cloud metadata (169.254.169.254).
  • The admin can disable or remove it in one click, and the audit log shows every call it got.

Full details: docs/threat-model.md.

16.4 Upgrade and rollback

helm upgrade tmg helm/team-mcp-gateway -n mcp -f helm/team-mcp-gateway/values-prod.yaml --set images.tag=1.0.1 --wait
helm -n mcp history tmg
helm -n mcp rollback tmg <revision> --wait
Helm rolls back Kubernetes objects, not data. Take a database backup before risky upgrades (commands in docs/production-vps.md).

18. Interview questions and simple answers

Q: Why is the gateway both an MCP client and an MCP server?
A: To the outside it is one MCP server (one URL, one key). To the upstreams it is a normal MCP client. It joins the tool lists and routes each call.

Q: How do you handle two servers with the same tool name?
A: Every tool gets the server name in front: server__tool. Server names cannot contain "_", so the split is never wrong. We show it with three ping tools.

Q: What happens if an upstream is slow or dead?
A: Listing uses a cache that is refreshed in the background in parallel, so it never waits. Calls have a 20 s timeout and return a clear error. A dead server is marked Unreachable with the reason; others keep working.

Q: How are API keys stored?
A: Only the SHA-256 hash and a short prefix. The full key is shown once. On each request we hash the given key and look it up. Revoked keys fail at once.

Q: Why SHA-256 for keys but scrypt for passwords?
A: Keys are 48 random hex characters, so they cannot be guessed; a fast hash is fine. Passwords are chosen by people and can be guessed, so we use a slow hash with salt.

Q: Why encrypt upstream credentials instead of hashing them?
A: We must send them to the upstream, so we need the real value back. Hashing is one-way; encryption is two-way. The key is in a Kubernetes Secret, not in the database.

Q: Why don't you pass the client's token to the upstream?
A: The upstream could steal and replay it against our gateway (confused deputy). Tokens should only be accepted by the service they were made for. The gateway checks the user, then uses the upstream's own credential.

Q: How does the chat agent act as the logged-in user?
A: It connects to the gateway's own /mcp with the user's login token. So it gets that user's tools and permissions, and every call is in the audit log under that user with via = chat.

Q: Why stateless Streamable HTTP?
A: Simple code, no session memory, any pod can answer. The cost: no server push, so clients must re-list tools to see a change.

Q: Where is isolation enforced?
A: Three places: (1) no Ingress for MCP servers and the DB (ClusterIP only); (2) NetworkPolicies, deny by default, MCP servers accept only the gateway; (3) a bearer token on each MCP server, known only to the gateway.

Q: How do secrets survive a Helm upgrade?
A: The Secret template uses lookup to read the existing Secret. If a value is there, it is reused; if not, a new random value is made.

Q: What would break with two gateway replicas?
A: The MCP endpoint is stateless and would be fine. SQLite on a ReadWriteOnce volume is the problem. We would move to Postgres. The health cache is per pod, which is fine.

Q: How does the WooCommerce MCP server authenticate to the store?
A: A WooCommerce REST API key (consumer key + secret). The setup Job writes it into WooCommerce's key table (hashed, like WooCommerce does), using values from the Secret. The MCP server gets the same values as env vars.

Q: Is the setup Job safe to run twice?
A: Yes. It checks "is WordPress installed?", "is the plugin installed?", "are there products?", and it replaces the API key row instead of adding a second one.

19. Limits and next steps

  • One gateway replica (SQLite). Next: Postgres + 2 replicas + rate limits per key.
  • New upstream connection per call. Next: a small connection pool.
  • No push of tool list changes to clients (stateless). Clients must reconnect to see changes.
  • Prompt injection from untrusted servers is reduced, not solved. Next: "pending review" for new servers, per-server tool allow-lists.
  • SSRF check does not cover DNS rebinding.
  • Invites are one-time passwords, not email links. OAuth on the gateway is not done.
  • Bonus multi-store provisioning was not attempted; we focused on a working core.
